03.The bar I build to

Why this is here: “it works on my machine” and “it survives production” are two different jobs. This is the standard I hold a backend to before I call it done — eight pillars, and the specific controls under each. Ticked items are ones I have shipped and operated; the rest I reach for when the system earns them.

shipped & operated applied when the system needs it

01Security

  • Signed session cookies — HMAC-SHA256, constant-time verify
  • Password hashing with scrypt, PII stored only as a salted hash
  • RBAC in middleware, before any handler runs
  • Row-level security on every table, writes via a service role
  • Origin-whitelisted CORS — never a wildcard
  • Rate limiting on public endpoints
  • Secrets in env, never in the repo — fail fast if missing
  • Schema validation on every inbound body, query and header

02API design

  • REST semantics that mean what they say — 202 for async, 204 for delete
  • Idempotency: every write has a natural key, so a retry is a no-op
  • Bounded, paged list endpoints — no unbounded result sets
  • One error shape across the whole surface, with a trace id
  • URL versioning with a documented deprecation window
  • OpenAPI spec committed alongside the code

03Performance

  • Indexes chosen from real query plans, not guesses
  • Slow work moved off the request path into workers
  • N+1 queries hunted down at the ORM boundary
  • Connection pooling sized to the box, not left at the default
  • Cache layers with explicit TTLs and invalidation on write
  • p95/p99 budgets per endpoint, not average latency

04Reliability

  • Exponential backoff with jitter on transient upstream failures
  • Repeat offenders parked in a cooldown so the backlog keeps draining
  • A reconciliation sweep that self-heals known fault modes
  • Health checks wired to a restart policy
  • Explicit timeouts at every level — connect, read, query, job
  • Dead-letter path for poison messages, with an alert on depth
  • Graceful shutdown: drain in-flight work, then exit

05Observability

  • Append-only audit tables — who did what, when, never updated
  • Structured logs with a request id, and no secrets in them
  • Error tracking with grouping and alerts on new failure types
  • RED metrics on every endpoint, USE metrics on the box
  • Distributed tracing once more than one service is involved
  • SLOs with an error budget, agreed before launch

06Data integrity

  • Forward-only migrations — added to, never edited
  • Expand → backfill → contract, so deploys need no downtime
  • Invariants as triggers and CHECK constraints, not just app code
  • Cascade deletes, so orphan rows cannot exist
  • Atomic claim on shared work — two workers never take one row
  • Soft deletes with a written retention policy
  • Backups with a restore actually tested, plus an RTO/RPO on paper

07Scalability

  • Stateless web tier — no session store pinning a user to one box
  • Files in object storage, not on the instance
  • Workers that scale out horizontally without a coordinator
  • A broker (Kafka / SQS / RabbitMQ) once the queue outgrows the database
  • CDN and edge caching for anything publicly cacheable
  • Partitioning before a table is big enough to hurt

08Delivery

  • CI on every commit — lint, tests, build, then deploy
  • Infrastructure as code in Terraform, environments separated
  • 12-factor config and a pinned runtime version
  • Containerised builds that run the same locally and in prod
  • Canary or blue-green when a bad deploy would be expensive
  • Deliberate fault injection, once there is enough to break

What I have not run in production: database sharding, CQRS with separate read and write models, and scheduled chaos engineering. I know the shapes and the trade-offs, but I would rather say that plainly than claim scars I do not have.

04.Inside a production backend

Scope note: the platform below is under NDA, so this describes the engineering rather than the client or the product. It is one system, broken into the layers it is actually built from — and what I built inside each one.

L1

API layer

90+ REST endpoints across session auth, resource CRUD, async job triggers, a multi-stage review workflow, and a CORS-gated external feed. Role checks run in middleware before any handler; long jobs return 202 and are polled rather than held open; list endpoints page in bounded chunks. The same routers mount in-process for a one-container deploy or run standalone — one codebase, two topologies.

Express · TypeScript · REST · RBAC middleware
L2

Data layer

18+ forward-only Postgres migrations — never edited, only added to. One universal join key that every domain table hangs off, cascade deletes so orphan rows can’t exist, JSONB where the shape is still moving, and append-only audit tables that are inserted into but never updated. Business invariants live in the database as triggers and CHECK constraints, so no application bug can bypass them.

Postgres · SQL migrations · JSONB · triggers · indexing
L3

Concurrency & pipeline layer

Long-running workers poll a status column and claim a batch atomically (pending → processing) so two processes never take the same row — no external message broker needed. Every write has a natural key, so a retry is a no-op instead of a duplicate. Transient upstream failures back off exponentially; repeat offenders get parked in a cooldown map so the backlog keeps draining. A scheduled reconciliation sweep self-heals four separate fault modes and keeps the pipeline eventually consistent.

Async workers · atomic claim · idempotency keys · backoff · self-healing sweep
L4

AI integration layer

Speech-to-text and LLM scoring wired in as first-class pipeline stages rather than bolted on: large structured JSON responses validated on the way back, retry and backoff on rate limits and 5xx, and rubric versioning deliberately decoupled from the governance workflow so editorial changes never invalidate historical scores.

Speech-to-text · LLM grading · structured output · rubric versioning
L5

Security layer

HMAC-SHA256 signed session cookies with constant-time verification and no server-side session store, scrypt password hashing, role-gated routes, and row-level security enabled on every table with all writes flowing through a server-side service role — a documented trade-off that concentrates authorization in one auditable middleware layer while leaving the door open to per-role database policies later. Private media is served through short-lived signed URLs, and PII is stored only as a salted hash.

HMAC sessions · scrypt · RBAC · row-level security · signed URLs · PII hashing
L6

Deployment layer

One codebase, two shapes: a single container running the web tier plus every long-running worker, or an esbuild-bundled serverless function for the stateless web tier with the polling workers hosted separately — because polling loops and in-memory state don’t survive serverless timeouts. Health checks with a restart policy, 12-factor env config that fails fast on a missing variable, and a pinned runtime version.

Railway · Vercel · esbuild · health checks · 12-factor config

Who you’d be working with

One engineer, end to end — from the migration file to the deploy that ships it.

No handoff between a “backend person” and a “DevOps person”. The schema, the workers, the auth, the pipeline and the infrastructure are one decision-set, and I would rather own all of it than negotiate across it.

  • Trade-offs written down. Every non-obvious choice gets a short note on what it costs and when to revisit it.
  • Built to be replaced. Clear seams, so the next engineer can pull out a layer without archaeology.
  • Boring where it counts. Novelty belongs in the model, not in the deployment story.
