01.Security

Authentication is not a feature you add later — it is the floor everything else stands on.

In production

HMAC-SHA256 signed session cookies with constant-time verification and no server-side session store. scrypt password hashing, role checks that run in middleware before any handler, and row-level security enabled on every table. Private media is served through short-lived signed URLs, and PII is stored only as a salted hash.

HMAC sessions · scrypt · RBAC middleware · row-level security · signed URLs · PII hashing

Controls

✓ shipped  ·  • when the system needs it

  • Signed session cookies — HMAC-SHA256, constant-time verify
  • Password hashing with scrypt, PII only as a salted hash
  • RBAC in middleware, before any handler runs
  • Row-level security on every table
  • Origin-whitelisted CORS — never a wildcard
  • Rate limiting on public endpoints
  • Secrets in env, never in the repo — fail fast if missing
  • Schema validation on every inbound body, query and header

the callRLS on, but every write goes through one service role

Row-level security is enabled on every table, yet authorization is concentrated in a single middleware layer instead of being expressed as per-role database policies.

Buys
One auditable place to read the access rules, and no policy drift between the database and the application as roles change.
Costs
The database cannot independently enforce who wrote what. A middleware bug is a real breach, not a contained one.
Undo when
A second write path appears — a direct client connection, or another service touching the same tables.

02.API design

The contract is the product for everyone integrating with you — including the team three months from now.

In production

90+ REST endpoints across session auth, resource CRUD, async job triggers, a multi-stage review workflow, and a CORS-gated external feed. Long jobs return 202 and are polled rather than held open; list endpoints page in bounded chunks; every error leaves with the same shape and a trace id.

Express · TypeScript · REST · 202 + polling · bounded pagination

Controls

✓ shipped  ·  • when the system needs it

  • HTTP semantics that mean what they say — 202 async, 204 delete
  • Idempotency: every write has a natural key, retry is a no-op
  • Bounded, paged list endpoints — no unbounded result sets
  • One error shape across the whole surface, with a trace id
  • URL versioning with a documented deprecation window
  • OpenAPI spec committed alongside the code

the callIdempotency by natural key, not by a key store

Every write derives a unique key from the data itself and leans on a database constraint, instead of a client-supplied Idempotency-Key cached in Redis.

Buys
Retry safety with no extra infrastructure and no TTL to expire at the wrong moment. The guarantee lives in the schema, so every code path inherits it.
Costs
It only prevents the duplicate — it does not replay the original response. Writes with no natural identity need the header approach instead.
Undo when
A client needs the first response back on retry, not merely the guarantee that nothing ran twice.

03.Performance

Average latency lies. The tail is what users actually feel, and the tail is where the bad queries hide.

In production

Indexes chosen from real query plans rather than guesses, and every expensive operation — transcription, model scoring, report generation — moved off the request path into workers so the API stays responsive under load. Eager loading at the ORM boundary keeps list endpoints from turning into N+1 loops.

EXPLAIN ANALYZE · composite indexes · async workers · eager loading

Controls

✓ shipped  ·  • when the system needs it

  • Indexes chosen from real query plans, not guesses
  • Slow work moved off the request path into workers
  • N+1 queries hunted down at the ORM boundary
  • Connection pooling sized to the box, not left at the default
  • Cache layers with explicit TTLs and invalidation on write
  • p95/p99 budgets per endpoint, not average latency

the callPoll for job status — don’t hold the connection open

Long jobs return 202 with a job id and clients poll for the result, instead of a held-open request, a websocket, or a webhook callback.

Buys
No connection held open per in-flight job, nothing to reconnect after a deploy, and it survives every proxy and serverless timeout in the path.
Costs
A latency floor equal to the poll interval, and a stream of requests that mostly answer “still running”.
Undo when
Clients need sub-second updates, or poll traffic starts costing more than a push channel would.

04.Reliability

Every dependency you have will fail. The only question is whether your system notices and keeps going.

In production

Transient upstream failures back off exponentially; repeat offenders get parked in a cooldown map so one bad dependency cannot stall the whole backlog. A scheduled reconciliation sweep self-heals four separate fault modes and keeps the pipeline eventually consistent. Health checks are wired to a restart policy rather than to a dashboard nobody reads.

Exponential backoff · cooldown parking · self-healing sweep · health checks

Controls

✓ shipped  ·  • when the system needs it

  • Exponential backoff with jitter on transient failures
  • Repeat offenders parked in a cooldown so the backlog drains
  • A reconciliation sweep that self-heals known fault modes
  • Health checks wired to a restart policy
  • Explicit timeouts at every level — connect, read, query, job
  • Dead-letter path for poison messages, with an alert on depth
  • Graceful shutdown: drain in-flight work, then exit

the callA self-healing sweep instead of a dead-letter queue

Rows that get stuck are recovered by a scheduled reconciliation pass that knows the fault modes, rather than being moved to a DLQ for a human to inspect.

Buys
Four known failure modes recover with nobody paged, and the backlog keeps draining straight through a bad upstream day.
Costs
It only heals what it was taught. A genuinely new failure mode sits there quietly, and there is no queue depth to alert on.
Undo when
Failures stop being enumerable, or a stuck record needs a human to look at it before it is retried.

05.Observability

If a customer is the one telling you the system is down, you did not have observability — you had hope.

In production

Append-only audit tables record who did what and when — inserted into, never updated, never deleted. Structured logs carry a request id through every stage of a job, so one identifier reconstructs the whole path, and secrets never reach them.

Append-only audit tables · structured logs · correlation id

Controls

✓ shipped  ·  • when the system needs it

  • Append-only audit tables — who did what, when, never updated
  • Structured logs with a request id, and no secrets in them
  • Error tracking with grouping and alerts on new failure types
  • RED metrics on every endpoint, USE metrics on the box
  • Distributed tracing once more than one service is involved
  • SLOs with an error budget, agreed before launch

the callThe audit trail is a table, not a log stream

Sensitive actions are written to append-only Postgres tables in the same transaction as the change itself, instead of being emitted into the logging pipeline.

Buys
The audit record commits or rolls back with the thing it describes, so the two can never disagree — and it is queryable with a join, not a log search.
Costs
It grows inside the OLTP database, needs its own retention plan, and is not free-text searchable the way logs are.
Undo when
Audit volume starts competing with production traffic for the same database.

06.Data integrity

Every other incident can be fixed with a deploy. Corrupt or missing data cannot.

In production

18+ forward-only Postgres migrations — never edited, only added to. One universal join key that every domain table hangs off, cascade deletes so orphan rows can’t exist, and JSONB where the shape is still moving. Business invariants live in the database as triggers and CHECK constraints, so no application bug can bypass them.

Postgres · forward-only migrations · triggers · CHECK constraints · cascade deletes · JSONB

Controls

✓ shipped  ·  • when the system needs it

  • Forward-only migrations — added to, never edited
  • Expand → backfill → contract, so deploys need no downtime
  • Invariants as triggers and CHECK constraints, not just app code
  • Cascade deletes, so orphan rows cannot exist
  • Atomic claim on shared work — two workers never take one row
  • Soft deletes with a written retention policy
  • Backups with a restore actually tested, plus an RTO/RPO on paper

the callForward-only migrations, expand → backfill → contract

A migration is never edited once merged, and destructive schema changes are split into three deploys instead of one.

Buys
Old and new code run against the same schema during a rollout, so deploys need no downtime and a rollback does not need a database restore.
Costs
Schema work takes three times as long, duplicate columns live in production for a while, and backfills have to be watched.
Undo when
Only on greenfield work, before a second environment or a single real user depends on the data.

07.Scalability

Most scaling problems are not throughput problems. They are state sitting in the wrong place.

In production

No server-side session store, so any instance can serve any request and the web tier scales out without sticky sessions. Uploads live in object storage, not on the box. Workers claim their work atomically straight from the database, so adding a second worker needs no coordinator and no config change.

Stateless web tier · object storage · atomic claim · horizontal workers

Controls

✓ shipped  ·  • when the system needs it

  • Stateless web tier — no session store pinning a user to a box
  • Files in object storage, not on the instance
  • Workers that scale out horizontally without a coordinator
  • A broker (Kafka / SQS / RabbitMQ) once the queue outgrows the database
  • CDN and edge caching for anything publicly cacheable
  • Partitioning before a table is big enough to hurt

the callThe database is the queue

Workers poll a status column and claim a batch atomically inside a transaction, rather than sitting behind Kafka, SQS or RabbitMQ.

Buys
One less system to run, monitor and pay for. Job state and business data commit together, so a crash cannot leave the two disagreeing.
Costs
A polling-interval latency floor, no free fan-out or replay, and throughput bounded by one Postgres instance.
Undo when
A second consumer needs the same events, or claim contention starts showing up in query plans.

08.Delivery

A change that cannot be shipped safely on a Friday afternoon is not finished.

In production

One codebase, two shapes: a single container running the web tier plus every long-running worker, or an esbuild-bundled serverless function for the stateless web tier with the polling workers hosted separately. 12-factor env config that fails fast on a missing variable, a pinned runtime version, and CI that lints, tests and builds on every commit.

Railway · Vercel · esbuild · Terraform · GitHub Actions · 12-factor config

Controls

✓ shipped  ·  • when the system needs it

  • CI on every commit — lint, tests, build, then deploy
  • Infrastructure as code in Terraform, environments separated
  • 12-factor config and a pinned runtime version
  • Containerised builds that run the same locally and in prod
  • Canary or blue-green when a bad deploy would be expensive
  • Deliberate fault injection, once there is enough to break

the callOne codebase, two deploy topologies

The same routers either mount in-process in one container alongside the workers, or bundle into a serverless function with the workers hosted separately.

Buys
The hosting decision stays reversible and cost-driven rather than architectural, and there is one place to fix a bug.
Costs
Two deploy paths to keep green, and a hard constraint to respect: polling loops and in-memory state do not survive serverless timeouts.
Undo when
Web tier and workers need to scale on genuinely different curves — then they earn separate repos and separate on-call.

What I have not run in production: database sharding, CQRS with separate read and write models, and scheduled chaos engineering. I know the shapes and the trade-offs, but I would rather say that plainly than claim scars I do not have.

Who you’d be working with

One engineer, end to end — from the migration file to the deploy that ships it.

No handoff between a “backend person” and a “DevOps person”. The schema, the workers, the auth, the pipeline and the infrastructure are one decision-set, and I would rather own all of it than negotiate across it.

  • Trade-offs written down. Every non-obvious choice gets a note on what it costs and when to revisit it — the eight above are that habit, in public.
  • Built to be replaced. Clear seams, so the next engineer can pull out a layer without archaeology.
  • Boring where it counts. Novelty belongs in the model, not in the deployment story.
