How I build software systems

Most teams can get a service running. What tends to be missing is everything that keeps it running — the retry that doesn’t duplicate a row, the migration that doesn’t take the site down, the worker that says something when it stops. 01 Security auth, authorization, secrets
Authentication

Verifying who is making the request before anything else happens. JWT for stateless sessions, OAuth 2.0 for third-party sign-in, API keys for server-to-server calls.

Authorization

Deciding what a verified caller is allowed to do. Roles cover the broad strokes; attributes like ownership, team or region cover the rest — checked on the server, never trusted from the client.

CORS

Declaring which origins a browser may call the API from. An explicit whitelist, because a wildcard hands the same access to any page on the internet.

Encryption

TLS for anything crossing a network, a slow hash for passwords, and field-level encryption for sensitive data sitting in the database.

Input validation

Checking every value that arrives from outside — body, query, headers, path — for type, length, format and range before it reaches any logic. One unvalidated field is the root of most injection bugs.

Rate limiting

Capping how many requests one caller can make in a window, so a single client cannot exhaust the service, scrape it, or brute-force a login.

Security headers

Response headers that tell the browser what it may do with the page — HSTS, a content security policy, nosniff, frame options. Cheap to set and expensive to omit.

02 API design the contract clients live with
API versioning

Keeping existing clients working when the contract changes, by serving the old shape at one path while the new one moves on, with a stated date for when the old one goes.

Idempotency keys

Making a repeated request produce the same result as the first. A client that retries after a network timeout gets the original answer instead of a second charge.

Cursor-based pagination

Paging with a pointer to the last row seen instead of an offset, so page one thousand costs the same as page one rather than scanning everything before it.

Request / response schema

A written contract for every endpoint's inputs and outputs, published as OpenAPI so documentation, client libraries and tests all read from one source instead of the code.

03 Performance latency where users feel it
Multi-layer caching

Holding answers closer to the caller at each level — in process, in Redis, at the CDN — each layer with its own lifetime and its own rule for when it is wrong.

Query optimization & indexes

Reading the plan the database actually produces, then adding the indexes it asks for and removing the N+1 loops it exposes. A missing index turns a 100 ms query into a five-second one under load.

Connection pooling

Reusing a fixed set of open connections — to the database and to outbound HTTP services — instead of opening a new one per request, so the handshake is paid once.

Compression

Compressing responses before they cross the wire. JSON typically drops 70–80%, and Brotli beats gzip on anything a modern browser fetches.

Async processing & background jobs

Moving slow work — email, exports, transcoding, model scoring — onto a queue so the request returns straight away with a job id instead of holding the caller open.

04 Reliability what happens when things fail
Circuit breaker

Failing fast once a dependency is clearly down, instead of queueing behind it, and probing occasionally to find out whether it has come back.

Retry with exponential backoff

Retrying a transient failure with a growing delay and a random offset, so every client does not come back at the same instant and knock the service over again.

Timeout strategy

An explicit deadline at every level — connect, read, query, whole request, background job — because the default is usually no deadline at all.

Graceful degradation

Deciding in advance what a page or endpoint does when an optional dependency is unavailable, so one feature failing does not take the rest of the product with it.

Health checks

Two separate answers: am I alive, and am I ready for traffic. The load balancer needs the second one, and the orchestrator needs the first.

Dead letter queue

A side queue for messages that keep failing, so one bad record cannot block everything behind it and somebody can inspect it later.

Graceful shutdown

On a stop signal: refuse new work, let in-flight work finish, close connections, then exit — rather than dropping whatever was mid-flight.

05 Observability seeing it before users do
Structured logging

Logging as JSON with fixed fields — timestamp, level, request id, user, duration — so logs can be searched, aggregated and alerted on, not just read.

Distributed tracing

Carrying one trace id across every service a request touches, so the slow step shows up on a single timeline instead of being guessed at.

Metrics

Rate, errors and duration for every endpoint; utilisation, saturation and errors for the machine underneath. Without them, 'is it healthy' is a feeling.

Error tracking

Capturing production exceptions with stack trace and context, grouped, so a genuinely new failure raises an alert instead of scrolling past in a log.

SLOs & error budget

A written reliability target and the amount of failure it permits, so 'is this good enough to ship' has a number attached rather than an opinion.

Audit logs

An immutable record of who did what and when, for the operations that matter — deletes, permission changes, payments, admin actions.

06 Data integrity the incident you can’t hotfix
Transactions & ACID

Grouping steps that must all happen or none of them, so a crash halfway through leaves no half-written state for somebody to clean up by hand.

Expand → backfill → contract migrations

Splitting a destructive schema change into three deploys — add the new shape, move the data, remove the old — so old and new code can run against the same database.

Database-level validation

Constraints in the database itself — NOT NULL, UNIQUE, CHECK, foreign keys — as the last line of defence for when the application code is wrong.

Soft deletes & retention

Marking a record deleted rather than removing it, with a written policy for when it is genuinely purged. Hard deletes lose the audit trail and break references.

Backup, RTO & RPO

Automated backups, restores that have actually been tested, and two agreed numbers: how long recovery may take, and how much data may be lost.

Read replicas & CQRS

Sending heavy reads to a replica, or to a separate read model, so a reporting query cannot slow down the writes that customers are waiting on.

07 Scalability state in the right place
Stateless & horizontal scaling

Keeping no per-user state on the server, so any instance can serve any request and adding capacity means adding instances rather than a bigger machine.

Message queues & event-driven design

Publishing events instead of calling services directly, so a slow or absent consumer does not take the producer down with it.

CDN & edge caching

Serving static assets and cacheable responses from a location near the user rather than from one origin on the other side of the world.

Sharding & partitioning

Splitting one very large table across partitions or machines, by range or by key, before its size makes ordinary queries and backups impractical.

08 Delivery code to production, repeatably
CI/CD pipeline

Every commit runs lint, tests, build and a security scan, then deploys itself — so there is no manual step where a human can forget one.

Infrastructure as code

Servers, databases, networking and permissions defined in version-controlled code, so an environment can be rebuilt rather than remembered.

Blue-green & canary deploys

Shipping to a parallel environment or a small slice of traffic first, watching the metrics, and only then sending everyone across.

Chaos engineering

Deliberately breaking things — killing a process, adding latency, dropping a connection — to learn how the system behaves before it happens unannounced.

Read this as the standard, not the résumé: it is the list I hold a backend to. Most of it I have shipped and operated. Database sharding, CQRS with separate read and write models, and scheduled chaos engineering I have not run in production — I know the shapes and the trade-offs, and I would rather say so plainly than claim scars I do not have.

Stack & tooling

A deliberately small stack. Every line below is something I reach for often enough to know where it breaks — open one for what it is actually doing in the systems above.

01 Programming language what everything is written in
  • Python

How I use it Python end to end — services, workers, data preparation and model code in one language, so there is no boundary where the tooling and the types stop agreeing.

02 Web framework how a service gets served
  • FastAPI

How I use it FastAPI for typed request and response models, dependency injection, and an OpenAPI spec generated from the code rather than maintained beside it and left to drift.

03 Databases where state lives
  • PostgreSQL
  • MongoDB
  • Supabase

How I use it Postgres by default — constraints, transactions and migrations are the whole point. MongoDB where the shape is genuinely still moving, and Supabase when a project needs Postgres plus auth and file storage without standing all three up separately.

04 Vector database retrieval for AI features
  • ChromaDB

How I use it ChromaDB for embedding storage and similarity search behind retrieval-augmented features — the index that decides what a model gets to read before it answers.

05 Infrastructure as code environments defined in code
  • Terraform

How I use it Terraform, so an environment is a file in the repository rather than a sequence of console clicks nobody wrote down. Plan before apply, state kept remote, dev and prod separated.

06 DevOps build, test, ship
  • Docker
  • Kubernetes
  • CI/CD
  • GitHub Actions

How I use it Docker so the container that runs in production is the one that ran locally, and Kubernetes when several of them need scheduling, scaling and restarting without somebody watching. GitHub Actions on every commit — lint, tests, build, then deploy, with no manual step to forget.

07 Cloud where it runs
  • AWS
  • Azure
  • Railway
  • Vercel

How I use it AWS and Azure at the IaaS layer when a workload needs that much control; Railway and Vercel as PaaS when it does not, and the time is better spent on the product than on the VPC.
