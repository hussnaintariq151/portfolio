How I build AI systems

A demo is easy. What is hard is the second week — when the inputs stop looking like the training data, when a prompt change quietly breaks something that worked, when nobody can say whether the new version is better or just different. Each pillar below opens into the practices it covers; open any one of those for what it actually is.

  • 2LLM grading pipelines in production
  • 5shipped RAG & agent projects

Scope note: the numbers above come from platforms that are under NDA, so this page describes the engineering rather than the client or the product.

01 Data & features what the model learns from
Data versioning

Pinning the exact dataset a run was trained on, so a result can be reproduced months later instead of approximately remembered.

Leakage checks

Making sure nothing from the future, or from the test set, reaches the model during training. Most too-good-to-be-true scores turn out to be this.

Labelling & rubric design

Writing down what a correct label actually means before anyone starts labelling, so two annotators looking at the same example reach the same answer.

Feature engineering

Turning raw columns into signals a model can use, and discarding the ones that only look useful because they encode the answer.

Class imbalance

Deciding deliberately how a rare class is handled — resampling, class weights, or a threshold moved after training rather than during it.

02 Modelling baselines before anything clever
Honest baselines

A trivial model first — majority class, a linear fit, a keyword rule — so the interesting one has something real to beat.

Cross-validation

Splitting the data so the score you measure is the score you would get on new data, rather than the one a lucky partition handed you.

Hyperparameter search

Searching the settings systematically and against a validation split, instead of tuning on the test set until the number looks good.

Fine-tuning

Adapting a pretrained model to a specific domain, once prompting has stopped paying for itself and there is enough labelled data to justify it.

Interpretability

Being able to say why a prediction came out the way it did — feature importance, attention, or a worked example someone can follow.

03 Evaluation turning “it feels better” into a number
A real evaluation set

A held-out set that looks like production, built before the model exists, and never trained on. Everything else depends on this one being right.

Metrics that match the decision

Choosing the metric from what the output is actually used for. Accuracy on an imbalanced problem tells you almost nothing.

Error analysis

Reading the wrong predictions one at a time and grouping them, because the pattern in the failures is where the next improvement is hiding.

LLM-as-judge & calibration

Using a model to grade outputs at scale, then checking it against human grades so the grader itself is measured rather than trusted.

Regression suite

A fixed set of cases that must keep passing, so a prompt or model change cannot quietly break what already worked.

04 Retrieval & RAG grounding an answer in something real
Chunking strategy

Deciding how a document is split before it is embedded. Too large and retrieval is vague; too small and the context that made it meaningful is gone.

Embeddings & vector search

Turning text into vectors and finding the nearest ones, so retrieval works by meaning rather than by matching keywords.

Reranking

A second, more careful pass over the top candidates, because the first retrieval is tuned for recall and the answer needs precision.

Grounding & citations

Making the answer point at the passage it came from, so a reader can check it and a hallucination becomes visible instead of plausible.

Retrieval evaluation

Measuring the retrieval step on its own. If the right passage never arrives, no amount of prompt work will fix the answer.

05 LLM engineering getting a model to behave
Structured output

Forcing the model to answer in a schema and validating it on the way back, so downstream code consumes data instead of parsing prose.

Prompt versioning

Treating a prompt as code — versioned, diffable, and tied to the evaluation run that approved it, so a change can be traced and rolled back.

Tool use & agents

Giving a model a set of functions it can call, with the loop and the stopping condition written by you rather than decided by the model.

MCP servers

Exposing tools and data to a model over the Model Context Protocol, so the same capability works across clients instead of being wired into one app.

Guardrails

Checks around the model — input filtering, output validation, refusal handling — because the model is not the last line of defence.

Retry & backoff

Handling a provider's rate limits and 5xx with growing delays and a cap, so a busy hour degrades rather than fails.

06 Serving & inference the model as an API
Model behind an API

Wrapping the model in a typed HTTP interface, so callers depend on a contract rather than on somebody's notebook.

Async & batching

Moving long inference off the request path, and grouping calls where the model is meaningfully faster per item in a batch.

Caching

Not paying twice for the same answer — cached embeddings, cached completions, cached retrieval for queries that repeat.

Cost & token budgets

Knowing what a request costs before it ships, and putting a ceiling on it, because token spend scales with traffic and nothing warns you.

Fallback models

A smaller or older model to fall back to when the primary one is slow, rate-limited or down, so the feature degrades instead of disappearing.

07 Monitoring & drift noticing when it stops working
Data drift

Watching whether production inputs still resemble the training data, because a model decays silently and nothing throws an error when it does.

Prediction monitoring

Tracking the distribution of outputs over time. A shift there is usually the first visible sign that something upstream changed.

Human feedback loop

Capturing corrections and overrides as labelled data, so the system improves from being used rather than only from being retrained.

Quality alerts

Alerting on the evaluation metric, not only on latency and error rate. A model can be fast, healthy and wrong at the same time.

08 MLOps & reproducibility the same run, twice
Experiment tracking

Every run's parameters, data version, code version and result recorded, so “which one was that” has an answer three months later.

Model registry

One place where a model version is registered, staged and promoted, rather than a file named final_v3 on somebody's laptop.

Reproducible runs

Pinned dependencies, fixed seeds and versioned data, so the same run produces the same numbers on a different machine.

CI/CD for models

The model pipeline in CI: tests, then an evaluation gate, then deployment — so a model that fails evaluation cannot ship.

Containerised inference

The same image locally and in production, so “it works on my machine” cannot apply to the model either.

Read this as the standard, not the résumé: it is the list I hold an AI system to. Most of it I have shipped and operated. Training a foundation model from scratch, RLHF and preference tuning, and multi-GPU distributed training I have not run in production — I know the shapes and the trade-offs, and I would rather say so plainly than claim scars I do not have.
